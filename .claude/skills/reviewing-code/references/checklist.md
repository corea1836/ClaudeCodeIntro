# 리뷰 체크리스트

바닐라 HTML/CSS/JS 단일 페이지 앱 기준이다. 각 항목은 "이런 곳에서 버그가 잘 숨는다"는 힌트이지, 모두 채워야 하는 양식이 아니다. 바뀐 코드와 관련 있는 절을 골라 읽는다.

## 목차
1. 정확성
2. 상태와 렌더링
3. 영속성 (localStorage)
4. 브라우저 API
5. 접근성
6. 보안
7. 성능
8. 유지보수성
9. 테스트

## 1. 정확성
- **경계값:** 후보 0개, 1개, 아주 많을 때. 빈 배열에 `Math.floor(Math.random() * n)`, 0으로 나누기, `items[undefined]`.
- **각도·모듈로 연산:** 음수 각도에 `%`를 쓰면 음수가 나온다(`mod` 헬퍼를 써야 함). 칸 경계에 정확히 걸칠 때 어느 칸으로 판정되는지, 부동소수 오차로 인덱스가 `n`이 되지 않는지.
- **랜덤:** 균등 분포인지(편향된 `Math.round` 사용 등), 결과를 먼저 정하고 애니메이션을 맞추는 구조라면 그려진 칸과 계산된 칸이 같은지.
- **날짜:** 로컬 날짜와 UTC 날짜(`toISOString()`은 UTC다)를 섞지 않는지. 자정을 넘겨 페이지를 열어 둘 때 "오늘"이 갱신되는지. 월말·연말·서머타임에서 `setDate(d - n)` 계산. 날짜 문자열 정렬이 `YYYY-MM-DD` 형식에 의존하는지.
- **문구:** 한국어 조사(은/는, 이/가)가 앞 단어 받침과 맞는지. 메뉴 이름이 바뀌면 깨질 수 있는 하드코딩 조사.

## 2. 상태와 렌더링
- 상태를 바꾼 모든 경로가 `render()`로 이어지는지. 렌더 누락은 "눌렀는데 화면이 안 바뀜"으로 나타난다.
- 같은 정보를 두 곳에 들고 있지 않은지(파생 상태). 예: 원판에 그려진 `state.items`와 `getCandidates()`의 결과가 어긋나는 시점.
- 비동기 구간(회전 애니메이션) 중에 다른 입력이 상태를 바꿀 수 있는지. 연타, 탭 전환, 필터 변경, 창 크기 변경, 다크 모드 전환.
- `render()`가 매번 DOM을 새로 만들 때, 포커스가 사라지거나 이벤트 리스너가 중복 등록되지 않는지.

## 3. 영속성 (localStorage)
- 모든 `getItem`/`setItem`이 try/catch 안에 있는지(사생활 보호 모드, 저장 공간 초과).
- `JSON.parse` 결과의 **형태**를 검증하는지. 배열인지만 보고 원소(`null`, `date` 없음, 숫자)는 안 보면, 나중에 `h.date.localeCompare` 같은 곳에서 터진다.
- 저장 키 이름을 바꾸면 기존 사용자 데이터가 사라진다. 바꿨다면 이전 키를 읽어 옮기는 코드가 있는지.
- 저장 데이터가 끝없이 늘어나지 않는지(표시는 30개만 해도 저장은 무한일 수 있음).

## 4. 브라우저 API
- **canvas:** `devicePixelRatio` 반영, 크기가 0일 때(숨겨진 상태) 처리, resize 후 다시 그리기.
- **matchMedia:** 다크 모드와 `prefers-reduced-motion` 변경을 실행 중에도 반영하는지, 처음 한 번만 읽는지.
- **requestAnimationFrame:** 탭이 백그라운드로 가면 멈춘다. 애니메이션이 끝나야 상태가 확정되는 구조라면 그동안 잠금이 풀리지 않는다.
- **전역 이름 충돌:** 클래식 스크립트의 최상위 변수는 `window.history`, `name`, `status`, `top`, `event` 같은 내장 전역을 가릴 수 있다.
- **`confirm`/`alert`:** 일부 임베드 환경(iframe sandbox)에서는 막혀서 항상 false를 돌려준다.

## 5. 접근성
- 역할 짝이 맞는지: `role="tablist"` → `role="tab"`(+ `aria-controls`, 방향키 이동) → `role="tabpanel"`. 짝이 안 맞으면 스크린 리더가 잘못 안내한다.
- 토글 버튼은 `aria-pressed`, 선택은 `aria-selected`가 실제 상태와 함께 갱신되는지.
- 결과 안내가 `aria-live` 영역으로 읽히는지, 같은 문구가 반복되면 다시 읽히는지.
- canvas는 스크린 리더가 내용을 모른다. 결과를 텍스트로도 제공하는지.
- 키보드만으로 모든 기능을 쓸 수 있는지, `:focus-visible` 표시, 터치 대상 크기(약 44px), 색 대비(특히 다크 모드에서 고정 색상을 쓴 곳).

## 6. 보안
- 저장소·URL·사용자 입력 데이터를 `innerHTML`, `insertAdjacentHTML`, `document.write`에 넣지 않는지. 이 앱은 `textContent`를 쓰는 것이 기준이다.
- 외부 스크립트, CDN, `eval`, `new Function` 추가 여부.

## 7. 성능
- 애니메이션 프레임마다 도는 코드에서 무거운 작업(`getComputedStyle`, 레이아웃을 읽는 속성, 큰 배열 재계산)을 하지 않는지.
- 한 번의 상호작용에 `render()`가 여러 번 불리지 않는지.
- 사람이 체감할 수준이 아니면 ⚪ Nit 이하로 둔다.

## 8. 유지보수성
- 매직 넘버(각도, 픽셀, 시간)가 이름 있는 상수인지.
- 함수 하나가 계산과 DOM 조작을 함께 하고 있다면 테스트하기 어렵다.
- 주석이 "무엇"이 아니라 "왜"를 설명하는지, 코드와 어긋난 주석은 없는지.

## 9. 테스트
- 바뀐 동작에 대응하는 테스트가 있는지. 없다면 "테스트 공백"에 적는다.
- 테스트가 구현 세부사항(내부 변수 이름)보다 사용자에게 보이는 동작(DOM, 저장소, 그려진 canvas)을 검증하는지.
- 랜덤·시간에 의존하는 테스트가 고정값으로 결정적인지. 실행할 때마다 결과가 달라지는 테스트는 신뢰할 수 없다.
- 테스트가 실제로 버그를 잡는지 의심되면, 코드를 일부러 망가뜨려(예: off-by-one) 테스트가 실패하는지 본다. 확인 뒤에는 반드시 원래대로 되돌린다.
