# 코드 리뷰

이 스킬의 목표는 **사람이 그대로 믿고 행동할 수 있는 리뷰**를 만드는 것이다. 지적이 많을수록 좋은 리뷰가 아니다. 근거 없는 지적 하나가 리뷰 전체의 신뢰를 깎으므로, 검증한 것만 확신을 갖고 말하고 나머지는 확신도를 낮춰 표시한다.

리뷰어는 코드를 고치지 않는다. 수정 방향은 제안하되, 무엇을 고칠지는 리포트를 읽은 사람이 정한다. 재현용 스크립트가 필요하면 프로젝트 밖 임시 디렉터리(`mktemp -d`)에 만든다.

## 1. 범위 정하기

- 사용자가 파일·함수·변경사항을 지정했으면 그것만 본다. 다만 바뀐 코드가 호출하거나 호출당하는 부분은 영향 범위이므로 함께 읽는다.
- git 저장소라면 `git status`와 `git diff HEAD`로 바뀐 부분을 먼저 확인한다. git이 아니거나 변경 범위가 없으면 `index.html`과 `tests/` 전체를 대상으로 한다.
- 리포트 첫머리에 무엇을 리뷰했는지 적는다. 읽는 사람이 리뷰가 다루지 않은 범위를 알아야 하기 때문이다.

## 2. 자동 검사 먼저 돌리기

```bash
npm run check   # lint(eslint) → build(html-validate) → test(node --test)
```

- `node_modules`가 없으면 `npm install`부터 한다.
- 실패한 항목은 그대로 리포트의 지적 사항이 된다. 테스트 실패는 보통 🔴 또는 🟠이다.
- 린터가 이미 잡는 스타일 문제(따옴표, 세미콜론, 미사용 변수 등)는 사람이 다시 지적하지 않는다. 사람의 리뷰는 도구가 못 보는 것, 즉 로직·스펙·사용자 경험에 쓴다.

## 3. 코드 읽기

1. 전체 흐름을 먼저 잡는다. 이 앱은 `state`와 저장소 값 → `render()` → DOM/canvas 순서로 흐른다. 이벤트 핸들러가 상태를 바꾸고 다시 render하는 구조인지 확인한다.
2. [references/checklist.md](references/checklist.md)의 관점(정확성, 상태·렌더링, 영속성, 브라우저 API, 접근성, 보안, 성능, 유지보수성, 테스트)으로 훑는다. 전부 기계적으로 대조하지 말고, 바뀐 코드와 관련 있는 관점에 시간을 쓴다.
3. 요구사항과 맞는지 [references/project-spec.md](references/project-spec.md)와 대조한다. 코드가 스펙과 다르면 어느 쪽이 맞는지 단정하지 말고 차이를 그대로 보고한다. 스펙 문서가 낡았을 수도 있다.

## 4. 지적 사항 검증하기

의심 가는 곳을 찾았다면 리포트에 쓰기 전에 실패 시나리오를 구체적으로 만든다. "어떤 입력·상태에서 → 무엇이 잘못되는가"를 한 문장으로 말할 수 없다면 아직 지적할 단계가 아니다.

가능하면 실제로 재현한다. `tests/load-app.js`의 `loadApp()`은 시간(2026-10-05 정오 고정), `Math.random`, 애니메이션 프레임, canvas, localStorage를 제어할 수 있는 jsdom 환경을 만들어 준다. 새로 만들지 말고 이것을 쓴다.

```js
// $TMP/repro.mjs  (실행: node $TMP/repro.mjs)
import { loadApp, daysAgo } from '<프로젝트 절대경로>/tests/load-app.js';

const app = loadApp({
  storage: { 'mealRoulette.history': [{ date: daysAgo(1), breakfast: '토스트', lunch: '라멘', dinner: '피자' }] },
  random: () => 0.5,
});
app.tab('점심').click();
app.spin();                              // 회전 애니메이션을 끝까지 진행
console.log(app.labelAtPointer(), app.slotNames(), app.message());
console.log(app.window.eval('JSON.stringify(state)')); // 내부 상태 확인
```

검증 결과에 따라 확신도를 붙인다.

- **확인됨**: 재현했거나, 코드 경로를 끝까지 따라가 틀림없이 일어남을 보였다.
- **가능성 있음**: 근거는 있지만 재현하지 못했다. 무엇을 확인하면 확정되는지 함께 적는다.

검증하다가 오해였던 것으로 밝혀진 의심은 버린다. 리포트에 "확인해 봤는데 문제없음"을 늘어놓지 않는다.

## 5. 리포트 작성

심각도는 사용자가 실제로 겪는 영향으로 정한다.

| 심각도 | 기준 | 예 |
|---|---|---|
| 🔴 Critical | 데이터 손실, 앱이 동작하지 않음, 보안 문제 | 저장된 히스토리가 지워짐, 스크립트 에러로 화면이 안 뜸 |
| 🟠 Major | 일반적인 사용 중 잘못된 동작, 스펙 위반 | 포인터가 가리킨 메뉴와 결과가 다름 |
| 🟡 Minor | 드문 조건에서만 생기는 문제, 접근성·견고성 | 아주 긴 메뉴 이름이 원판 칸 밖으로 넘침 |
| ⚪ Nit | 가독성, 이름, 작은 정리 | 매직 넘버를 상수로 |

Nit은 최대 5개까지만 적는다. 사소한 지적이 많으면 중요한 지적이 묻힌다.

아래 형식을 그대로 쓴다.

```markdown
# 코드 리뷰: <대상>

**리뷰 범위:** <파일/변경사항, 다루지 않은 범위가 있으면 함께>
**자동 검사:** lint ✅/❌ · build ✅/❌ · test ✅/❌ (<통과 수>/<전체>)
**결론:** <머지 가능 | 수정 후 머지 | 수정 필요> — <한 줄 이유>

## 지적 사항

### 🟠 [M1] <한 줄 요약>
- **위치:** `index.html:428`
- **확신도:** 확인됨 (재현 스크립트로 확인)
- **문제:** <무엇이 왜 잘못되었나>
- **실패 시나리오:** <어떤 입력/상태 → 어떤 잘못된 결과>
- **제안:** <고치는 방향, 필요하면 짧은 코드>

(심각도 높은 순. 번호는 C1, M1, m1, n1 처럼 심각도 머리글자 + 순번)

## 테스트 공백
- <테스트로 보호되지 않는 중요한 동작과, 추가하면 좋을 테스트 한 줄 설명>

## 잘된 점
- <근거가 있는 것만 1~3개. 칭찬을 위한 칭찬은 쓰지 않는다>
```

지적 사항이 없으면 "지적 사항 없음"이라고 쓰고, 무엇을 확인했는지 두세 줄로 남긴다. 결론은 다음 기준으로 고른다. 🔴가 하나라도 있으면 "수정 필요", 🟠가 있으면 "수정 후 머지", 그 외에는 "머지 가능".
